You are given a code repository in the current directory.

Task: Implement *runtime* deprecation for Falcon’s asyncio convenience aliases exposed from `falcon.util` (and any top-level `falcon` re-exports), for a 4.x release. These aliases must be removed in Falcon 5.0.

Goal
- User code that uses the Falcon-provided asyncio aliases must receive a deprecation warning at runtime.
- Falcon’s own internals and test suite must not emit these warnings during normal operation (including when warnings are treated as errors).

Read this carefully: previous attempts failed because they (a) added wrappers that warned, but (b) did not migrate all internal and test call sites off the aliases, resulting in warning spam and test failures. Your work must avoid that.

Key symbols to deprecate
- Identify the exact asyncio-related convenience aliases currently exposed from `falcon.util` (and any `falcon` top-level re-exports). Likely examples include `create_task` and `get_running_loop`, but do not assume only those exist—confirm by searching the repo.
- Confirm definitions and re-exports by searching for:
  - `asyncio.` usage in `falcon/util`
  - alias names in `falcon/util` and `falcon/__init__.py` (or other re-export modules)
  - internal imports: `from falcon.util import ...` and `falcon.<name>` usage

Hard constraints (must satisfy all)
1) No internal deprecation warnings
- Falcon internal modules must not call deprecated aliases anymore.
- Do not “solve” this by globally filtering/silencing warnings inside Falcon. Fix call sites instead.

2) Preserve public semantics
- Do not change the alias behavior beyond emitting a warning for user calls.
- Preserve call signatures and accepted parameters across supported Python versions (notably `asyncio.create_task` gained keyword-only args such as `name` and `context` depending on Python version). Avoid narrowing the signature.
- Avoid introducing import-time side effects or circular imports.

3) Robust under strict warnings
- The full Falcon test suite must pass when warnings are treated as errors for the deprecation warning type you introduce.
- Assume downstream users may run with `-W error`.

4) Tests must prove two things
- Calling the deprecated alias from “user code” emits exactly one deprecation warning of the correct category and with an actionable message.
- Running representative Falcon internal code paths does not emit this deprecation warning (aim for zero warnings of that category).

Important design guidance (to avoid previous failure modes)
- Do not simply replace `create_task = asyncio.create_task` with a decorated Python wrapper and leave internal calls unchanged. That caused warning spam and also changed introspection characteristics.
- Prefer a deprecation mechanism that preserves the alias as a direct reference to the original callable as much as possible, while still warning when accessed/used by user code.
- Strongly preferred approach: emit the deprecation warning at attribute access time via module `__getattr__` (PEP 562) or an equivalent pattern, so the alias can remain a direct assignment internally and warnings can be tightly controlled. This also helps preserve the original callable’s signature and behavior.
  - Example idea (do not copy blindly; adapt to Falcon patterns): keep the real alias name out of the module globals (or keep an internal name), and implement `falcon.util.__getattr__` (or the specific util submodule’s `__getattr__`) to return `asyncio.create_task` while warning.
  - Also handle `__all__` and `dir()` expectations carefully.
- If you choose wrappers anyway, you must:
  - exactly forward all args and kwargs,
  - preserve keyword-only behavior,
  - avoid import cycles,
  - and still ensure Falcon internals do not call the wrapper (migrate all internal and tests call sites). But prefer `__getattr__` to avoid wrapper identity/signature breakage.
