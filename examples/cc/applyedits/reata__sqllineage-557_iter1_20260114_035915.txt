Implement metadata-driven target column inference for INSERT INTO … SELECT when the target column list is omitted, and ensure it works for both sqlfluff and sqlparse analyzers.

Goal
When an INSERT INTO … SELECT … statement does not specify a target column list, infer the target column names from MetaDataProvider and use them as the target-side columns in column lineage, provided the number of inferred target columns matches the number of columns in the SELECT list. This should make the lineage behave as if the SQL had explicitly specified the target columns.

Example
- SQL: insert into target select user_id, user_name from source
- Physical target columns: id, name
- Expected lineage edges:
  - source.user_id -> target.id
  - source.user_name -> target.name
- Only apply inference when lengths match. Do not override explicit target column lists.

Where to change
- The main logic for the sqlfluff analyzer path is in SourceHandlerMixin.end_of_query_cleanup in sqllineage/core/parser/__init__.py. You will add a metadata-based fallback mapping there.
- For the sqlparse analyzer path, SourceHandlerMixin is also used, but today handlers don’t receive metadata_provider. You must pass metadata_provider to sqlparse handlers in sqllineage/core/parser/sqlparse/analyzer.py so that SourceHandlerMixin can access it via getattr(self, "metadata_provider", None).
- Verify if sqlfluff handlers already receive metadata_provider; if not, propagate there similarly.

What to implement
1) Tests first (to reproduce the bug), then code change, then verification. Remove the test files before finalizing the commit if required by this repository’s contribution policy.

2) Extend SourceHandlerMixin.end_of_query_cleanup:
- Keep existing behavior that if len(holder.write_columns) == len(col_grp), use holder.write_columns[idx] as the resolved target column.
- Otherwise, if a metadata provider is available and the write target is a concrete Table, fetch target table columns via metadata_provider.get_table_columns(tgt_tbl). If and only if the number of returned columns equals len(col_grp), use the column at the same index idx as tgt_col_resolved.
- Only perform this mapping when the lengths match; otherwise, keep current behavior (using target-side names from the SELECT list).
- Ensure the resolved target column’s parent is the target table. The metadata provider should return Columns already parented to the table; if not, set it.
- Do not change wildcard expansion logic or any unrelated logic. Do not override explicit target column lists (holder.write_columns) if present.

3) Propagate metadata_provider into sqlparse handlers:
- In sqllineage/core/parser/sqlparse/analyzer.py, where DML handlers are instantiated (e.g., _extract_from_dml), set metadata_provider on each handler instance so that SourceHandlerMixin can read it with getattr(self, "metadata_provider", None).
- If required, also ensure the sqlfluff analyzer path passes metadata_provider to its handlers in sqllineage/core/parser/sqlfluff/analyzer.py.

Acceptance criteria
- With a MetaDataProvider that defines the target table’s columns, an INSERT INTO … SELECT without an explicit target column list produces column lineage edges that use the target table’s actual column names.
- Behavior is unchanged when metadata is not available or when the number of metadata columns does not equal the SELECT-list length.
- Explicit target column lists continue to work unchanged via holder.write_columns.
- Both sqlfluff and sqlparse analyzer paths behave correctly with this mapping.
- The new tests pass after the fix, and tests are removed prior to final submission if required.

Implementation tips and pitfalls
- Only attempt metadata-based mapping when the write target is a concrete Table. Do not attempt for SubQuery, CTE, or Path targets.
- Only map when counts match exactly to avoid ambiguous mappings.
- Parent assignment matters: Column identity comparisons in this codebase depend on both name and parent. Use the Column objects returned by metadata_provider.get_table_columns (they should already be parented to the target Table); if not, set the parent explicitly.
- Respect ordering: map by index using the SELECT-list order within each union barrier group.
- Do not alter wildcard expansion logic; it is handled elsewhere (e.g., SubQueryLineageHolder.expand_wildcard).
- Keep the code changes minimal and localized to the selection of tgt_col_resolved and to metadata propagation in the sqlparse analyzer.
