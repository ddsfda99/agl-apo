# Issue to fix
**W2001 “Parameter not used” false positive when using `Fn::Transform` (`AWS::Include`) in `AWS::ApiGateway::RestApi` `Properties.Body`**  
*cfn-lint version: 0.55.0*

## Scenario
A CloudFormation template (`api.cfn`) includes an OpenAPI/Swagger file (`api-specification.yml`) using:

```yaml
Body:
  Fn::Transform:
    Name: AWS::Include
    Parameters:
      Location: ./api-specification.yml
```

The included file contains intrinsic functions like `Fn::Sub` referencing template parameters (e.g., `${PetLambdaArn}`, `${UserPoolArn}`). cfn-lint currently warns W2001 that these parameters are unused because it only scans the main template, not the included file.

## Required behavior
Parameters referenced in the included file must be treated as **used** for purposes of **W2001**.

## Non-negotiable constraints (based on previous failures)
1. **No broad suppression**: Do not disable/short-circuit W2001 when any `Fn::Transform`/`AWS::Include` appears.
2. **No nonstandard `${{...}}`**: Only support real CloudFormation `Fn::Sub` syntax (`${Param}`), consistent with existing cfn-lint behavior.
3. **Avoid global side effects**: The last attempt changed integration snapshot counts/exit codes. Your fix must be **narrowly scoped** so other templates don’t suddenly change warnings.
4. **Do not do rule-local “scan everything”**: Avoid filesystem I/O inside W2001 that walks all `Fn::Transform` occurrences across the whole template.
5. **Relative path resolution must be correct**: Resolve `Location: ./file.yml` relative to the **directory of the template file**.

# What to implement (scoped + consistent)
Implement support so that when the template contains an `Fn::Transform` with `Name: AWS::Include` **specifically under**:
`Resources/<logicalId>/Properties/Body` of a resource of type `AWS::ApiGateway::RestApi`,
the linter:
1. Resolves the `Location` file path (only local relative paths are required; remote/S3 may be skipped gracefully).
2. Loads/parses the included YAML/JSON.
3. Detects parameter usage inside the included structure, at minimum:
   - `Ref: SomeParam`
   - `Fn::Sub: "…${SomeParam}…"` (string form)
   - `Fn::Sub: ["…${SomeParam}…", {...}]` (list form; parse only the template string for `${...}` placeholders, but respect existing semantics)
4. Feeds discovered parameter names into the same “used parameter” computation that W2001 relies on.

## Critical: reuse existing semantics for `${...}` extraction
Do **not** invent new regexes that over-match. Reuse cfn-lint’s existing `Fn::Sub` parameter extraction logic if it exists (e.g., `Template.get_sub_parameters` / existing regex constants), so behavior matches the rest of the tool (including ignoring `${!Literal}` and handling pseudo parameters consistently).

## Parsing approach (avoid accidental matches)
The included OpenAPI file is not a full CFN template. Parse it as YAML/JSON data, then only treat **explicit dict shapes** as intrinsics:
- A mapping with exactly the key `"Ref"` and a string value
- A mapping with exactly the key `"Fn::Sub"` and value either string or list form
Do not treat arbitrary strings containing `${...}` as intrinsic usage unless they are inside an explicit `Fn::Sub`.

## Where to hook this (preferred)
Prefer integrating this into shared template preprocessing / transform handling (something like `Template.transform_pre` or similar) so W2001 can consume a precomputed “used parameters from includes” set without doing ad-hoc file I/O in the rule.

If that is too invasive, an acceptable fallback is to extend W2001 to consult a helper that:
- Is **scoped** to RestApi Body includes only
- Does not scan all transforms across the template
- Does not add new warnings/errors by itself
- Caches results per template instance to avoid repeated reads
