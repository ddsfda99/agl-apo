Technical concerns in the implemented change
5) Using threading.Lock in an asyncio context:
   - While acquiring a standard threading.Lock briefly for a simple counter will “work” in a single-threaded event loop, it is generally discouraged to block the event loop with synchronous locks. asyncio.Lock would be more idiomatic and avoids any risk of blocking the loop, even if minimal here.

6) Semantics of the concurrency counter:
   - The counter is incremented after acquiring the semaphore but before awaiting do_process_update. This will accurately reflect “currently being processed” only if subclasses of BaseUpdateProcessor synchronously await the coroutine. If a subclass decides to schedule the coroutine in the background and return early (contrary to SimpleUpdateProcessor), the counter can decrement too early or provide misleading values. At minimum, this should be documented or the design adjusted to account for such behavior if that’s a realistic extension point.
