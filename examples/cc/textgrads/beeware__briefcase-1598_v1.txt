Summary of what happened and why it failed

- The underlying bug is correctly identified: openSUSE/SLES rpmbuild omits the distro tag (%{?dist}) in the output RPM filename, while Briefcase’s LinuxSystemMostlyPassiveMixin.distribution_filename() always includes a distro tag segment for “rpm”, leading to FileNotFoundError when moving the built RPM to dist.

- You wrote unit tests that reproduce the bug by asserting the constructed RPM filenames for Fedora (should include distro tag and ABI) and openSUSE/SLES (should omit distro tag). Those tests were appropriate and minimal, and they failed initially for the SUSE cases, reproducing the problem.

- You then edited src/briefcase/platforms/linux/system.py to make distribution_filename() omit the distro tag segment for SUSE-like targets using safe checks with getattr on target_vendor_base/target_vendor. This is the right place and the right logic. After the change, your new SUSE tests pass, and Fedora still includes the distro tag, so the bug is fixed.

Where the run failed and what went wrong

- The full test suite failed due to an unrelated test: tests/commands/base/test_paths.py::test_data_path_creation_failure. This test expects directory creation to fail when attempting to create a path under /etc on Linux/macOS. However, the tests appear to be running as root in the CI/container, so os.makedirs("/etc/mydatadir") succeeds. The test monkeypatches subprocess.run, but that patch only affects the Windows branch in BaseCommand.validate_data_path; on Linux, os.makedirs is used directly, so the monkeypatch never triggers. As a result, the expected BriefcaseCommandError is not raised and the test fails.

- This failure is unrelated to your RPM filename change, but because you ran the entire test suite, it prevented a clean run. You didn’t investigate or explain this flakiness, which is caused by running the suite as root. This made it look like your changes caused a regression, even though they didn’t.

- You did not adjust or skip the failing test (and you shouldn’t alter that test), but you also didn’t mention that in an environment that runs as root, the test is invalid as written because the root user can write in /etc. The test relies on a permission error to simulate a failure, which won’t happen under root.

Concrete details of the bug and fix

- Original behavior in distribution_filename() for “rpm”:
  - Always returned app_name-version-revision.{rpm_tag}.{rpm_abi}.rpm.
  - On openSUSE, rpmbuild emits app_name-version-revision.{rpm_abi}.rpm (no distro tag), so briefcase’s move step looked for the wrong filename and failed with FileNotFoundError.

- Fixed behavior:
  - If target_vendor_base == "suse"
    or target_vendor starts with "opensuse"
    or target_vendor starts with "sles":
    return app_name-version-revision.{rpm_abi}.rpm.
  - Else, return the original app_name-version-revision.{rpm_tag}.{rpm_abi}.rpm.

- You used getattr to guard against missing target_vendor_base and target_vendor attributes in tests.

- This matches openSUSE/SLES rpmbuild output (e.g., helloworld-0.0.1-1.x86_64.rpm) and preserves Fedora/RHEL behaviors (e.g., helloworld-0.0.1-1.fc37.x86_64.rpm or helloworld-0.0.1-1.el9.x86_64.rpm).
