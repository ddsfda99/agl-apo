Root cause and likely failure mode
The template uses AWS::LanguageExtensions with Fn::FindInMap’s fourth argument “DefaultValue: !Ref AWS::NoValue”. The intent is that:
- When the mapping lookup fails, DefaultValue should be used.
- If DefaultValue resolves to AWS::NoValue, the property should be removed, which should suppress E3012 type violations for the removed property.

Two places govern this:
1) Validation schema for Fn::FindInMap (src/cfnlint/rules/functions/FindInMap.py)
2) Resolution logic for Fn::FindInMap (src/cfnlint/jsonschema/_resolvers_cfn.py) and the LanguageExtensions transform (src/cfnlint/template/transforms/_language_extensions.py)

The code currently has decent resolver and transform handling:
- _language_extensions._Transform detects the presence of DefaultValue and sets default_on_resolver_failure. If the map can’t be resolved, it returns the DefaultValue. If the default resolves to AWS::NoValue (handled in _ForEachValueRef), it returns None. The walking logic deletes keys with None, so Properties get removed as desired.
- _resolvers_cfn.find_in_map respects DefaultValue and avoids emitting missing mapping key errors when default is present. It also yields values and annotates the path to DefaultValue.

However, the Fn::FindInMap schema validation for DefaultValue is too restrictive under LanguageExtensions:
- In FindInMap.schema, when LanguageExtensions are enabled, the 4th item schema is an object with DefaultValue and a custom keyword “default_value”.
- The custom validator _default_value evolves the validator with context.functions=["Ref"] and then descends into the instance with type constraints (“array” + singular_types). This means only “Ref” is allowed inside DefaultValue and intrinsic functions like Fn::Sub, Fn::Join, Fn::If, etc., are disallowed.
- Realistic and valid LanguageExtensions usage expects DefaultValue to be able to use intrinsic functions beyond Ref (e.g., Fn::Sub, Fn::Join, Fn::If, Fn::Select, Fn::ToJsonString, possibly Fn::Length). The current validation would reject these, causing E1011 or related schema validation errors in cases covered by tests.
