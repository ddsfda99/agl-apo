What the issue is
- The problem arises in the fetchart plugin when a candidate image requires more than one operation (e.g., both downsizing due to max_filesize and reformatting due to cover_format). The current validation logic in Candidate._validate returns only one “check” value (a single operation), in priority order: downscale -> downsize -> deinterlace -> reformat -> exact.
- In the scenario described (a large PNG over max_filesize with cover_format=JPEG), Candidate._validate returns CANDIDATE_DOWNSIZE and never reaches CANDIDATE_REFORMAT. Then, Candidate.resize only does one operation based on self.check, so only downsizing is attempted. With PIL, downsizing by file size only works effectively for JPEG; for PNG, “quality” knobs do not apply, so the resize won’t reduce the PNG filesize reliably. This leads to incorrect behavior where the image is not converted to JPEG before trying to hit the max_filesize target.

Analysis of the existing code paths
- beetsplug/fetchart.py: Candidate._validate has early returns for a single operation, resulting in only one of downsizing or reformatting being requested.
- beets/util/artresizer.py:
  - PILBackend.resize tries to reduce filesize by lowering JPEG quality. This approach is ineffective for PNGs because PNG is lossless and Pillow’s save() for PNG ignores JPEG-specific options.
  - ArtResizer.reformat allows converting formats, and can take a deinterlaced flag. This is the right tool to convert PNG to JPEG before trying to reduce filesize.

What the agent changed
- The agent modified Candidate.resize to ignore self.check and to recompute which operations are needed, then apply them in a safe sequence:

  3) Resize either to maxwidth (downscale) or to the current max dimension (downsizing-only path) with max_filesize budget.
- This approach is sound and addresses the core issue: when both reformat and downsize are needed, reformat happens first, ensuring the resize step can apply JPEG-specific filesize reduction.
