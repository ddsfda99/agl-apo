## What the correct fix likely is (based on the prompt + existing tests)

The inconsistency exists because:

- **Symbolic mode** calls `compute_output_spec()` → `compute_output_shape()` and hits the validation.
- **Eager mode** often bypasses `compute_output_shape()` and may not perform equivalent validation at runtime.

So to make behavior consistent *without changing API semantics*, you should:

### A) Keep the validation in `compute_output_shape`
Don’t delete it; it encodes the intended constraint per existing tests.

### B) Add the same validation to runtime execution
Implement runtime checks early in `call()` (or `build()` / `call()` before projections), in a way that works for eager tensors too.

Common approach:
- If both last dims are statically known: check and raise immediately.
- If dynamic: optionally insert a runtime assert (backend-dependent) or skip if not supported, but at least align torch eager with symbolic for known shapes.

Example sketch (conceptual):
- In `call()`:
  - read `query.shape[-1]` and `value.shape[-1]`
  - if both are not `None` and unequal → raise `ValueError` with same message

This would make eager torch tensors raise as well (since they have concrete shapes).

### C) Add/adjust tests properly
- Restore `query_value_dim_mismatch` in `test_shape_mismatch_error`
- Add a new test that calls the layer eagerly with mismatched last dims and asserts it raises (for trainable backends; skip numpy backend if needed)
