## Root cause: schema rewrite broadened validation in unintended ways

The agent “fixed” Step Functions ASL validation by **rewriting the entire** `src/cfnlint/data/schemas/other/step_functions/statemachine.json` via a big `Write` operation.

This is the core problem. That file is a shared schema used for ASL validation; replacing it wholesale is extremely risky because:

1. **It can inadvertently change rules/validation behaviors outside the intended new keywords** (ItemProcessor, *Path variants, choice operators).
2. It can introduce subtle schema mistakes that cause new failures in real-world templates (here: QuickStart openshift).
3. It can alter typing constraints (integer vs number), required fields, additionalProperties behavior, etc., which can create *new* errors or warnings.

The integration failure confirms that happened: `openshift.yaml` now triggers an extra match.

### Specific schema regressions introduced

Even from the snippet of the original schema shown earlier, the rewrite changed a lot more than requested:

- `TimeoutSeconds` at top-level changed from **integer** to **integer** (ok) but earlier it was `integer`, later agent uses `integer` elsewhere and sometimes `number` (inconsistent).
- Multiple spots contain invalid JSON Schema keywords:
  - `types` used instead of `type` inside many items (`"types": "object"`). That was already present in the original file in several places, but rewriting the file makes it much harder to ensure you didn’t amplify such issues.
- The new `map` schema:
  - Previously required `Iterator`. Agent changed to:
    - `required: ["Type"]`
    - `oneOf`: required `Iterator` OR `ItemProcessor`
  - This is correct conceptually, but the overall Map object’s `additionalProperties:false` + new `oneOf` structure may now validate differently and create new errors in nested cases.
- Choice operator:
  - Added many new fields (good), but the agent did **not** model the important invariant that most choice operators require both `Variable` and one comparator *except* for some special ones; the existing schema already didn’t enforce `Variable` strictly, and the rewrite continues to not enforce it. This broadens what is accepted and might also change error reporting order/quantity.

The point: the task required “add support for X fields”; the agent applied a **schema redesign** instead of a minimal extension, and that impacted unrelated integration expectations.

### 1) Find the exact extra lint finding (must-do)

- `cfn-lint --include-checks I --include-experimental --configure-rule E3012:strict=false --format json -- test/fixtures/templates/quickstart/openshift.yaml > /tmp/new.json`

Until the extra finding is identified, you’re guessing.

### 2) Revert “rewrite” strategy: patch schema minimally
Once you know the extra finding is caused by StepFunctions schema changes, fix by:
- reverting the file to original and applying **minimal targeted additions**:
  - add only the new properties to the appropriate `task`, `fail`, `choice.Operator`, and `map` definitions
  - update Map to allow `ItemProcessor` in addition to `Iterator` without altering unrelated parts.

This avoids changing schema behavior in other places and is the safest way to keep integration outputs stable.

### 3) Ensure schema changes don’t impact QuickStart templates
After minimal patch:
- re-run the openshift scenario and ensure output matches expected 35.
- run full suite.

### 4) Avoid overwriting files wholesale
Use surgical edits:
- `Edit` on only the relevant JSON fragment
- add tests by appending new parametrized cases, not rewriting files.
