How to fix and improve robustness
1) Validate model IDs before calling
- Maintain a configuration-driven registry of allowed model IDs for each provider/environment (e.g., per tenant or region).
- On startup or before first call, query the provider’s list of deployed models and cache them. Use this cache to validate the requested model name.
- Enable pre-call checks. If the requested model is not in the deployed set, select a fallback or prompt the user to choose an available model.

2) Implement smart retry with backoff
- For HTTP 429:
  - Respect Retry-After header if present; otherwise default to provider guidance (e.g., 5 seconds).
  - Use exponential backoff with jitter: e.g., base delay 1–2s, multiply by 2 per attempt, add random jitter, cap at a max (e.g., 30s), limit attempts (e.g., 3–5).
  - If error indicates “No deployments available,” do not hammer the same deployment; pivot to an available model/deployment immediately.
- For transient 5xx errors, similar backoff policies apply.
- Ensure retry logic is idempotent and preserves conversation state.

3) Fall back to an available model
- Define a model fallback chain per capability class. For example:
  - Sonnet-tier → fallback to another Sonnet deployment/version → fallback to Haiku-tier if acceptable.
- Use capability-based selection (reasoning, JSON-mode, tool-use) rather than hardcoding a single model identifier.
- If all fallbacks fail, surface a clear message and offer to proceed with a lower-tier model or queue the task.

4) Respect cooldown_list and use a circuit breaker
- Maintain a cooldown map keyed by deployment/model ID. If a deployment is in cooldown_list or returns repeated failures, trip a circuit breaker for a TTL (e.g., 1–5 minutes) and route traffic away.
- Periodically re-check availability to close the circuit.

5) Preserve user context and retry safely
- Store the original prompt and any tool/context inputs so retries and fallbacks can reissue the same request without losing information.
- Ensure partial progress and streamed outputs are handled: if a retry starts, cancel the previous stream cleanly.

6) Logging and observability
- Log the model ID used, the provider response code, error message, and retry attempts.
- Emit metrics for 429 rates, retry success, fallback usage, and circuit breaker events to detect systemic issues early.

7) Timeouts and concurrency limits
- Set reasonable request timeouts and concurrency limits to avoid tripping rate limits.
- Use a token bucket or semaphore to throttle calls per model/provider based on known quotas.

8) Configuration hygiene
- Avoid speculative or future-dated model IDs. Keep model names in config, versioned per environment, and update them through release processes.
- Provide an admin or automated job that refreshes available deployments regularly and updates the registry.

9) User-facing resilience
- If a fallback occurs, notify the user succinctly: “Selected model is currently unavailable; using X as fallback.” Offer a switch back when availability returns.
- If repeated failures occur, provide actionable guidance: “Please select an available model from: …” or “We’ll retry in the background and notify you.”

10) Testing
- Unit tests for:
  - Model ID validation against a mock deployment list.
  - Retry/backoff logic with simulated 429 and Retry-After.
  - Circuit breaker behavior and cooldown handling.
  - Fallback chain selection rules.
- Integration tests against a sandbox environment that triggers rate limits and deployment unavailability.
- Load tests to ensure throttling avoids 429s under concurrency.
