Root cause of the bug
- The RPM file naming logic in distribution_filename assumed all RPM-based distros include a distro tag (e.g., .el9 or .fc37) in the RPM filename. OpenSUSE omits this distro tag; it produces RPMs named like helloworld-0.0.1-1.x86_64.rpm.
- As a result, Briefcase expected a file with a distro tag and attempted to move non-existent helloworld-0.0.1-1.el20240109.x86_64.rpm, causing FileNotFoundError.

Where in the code this happens
- src/briefcase/platforms/linux/system.py, in LinuxSystemMostlyPassiveMixin.distribution_filename() for the "rpm" packaging format:
  - Original logic always returned name-version-revision.{rpm_tag}.{rpm_abi}.rpm.
  - This was correct for RHEL/Fedora but wrong for SUSE (openSUSE / SLES).

What the agent changed
- They modified distribution_filename() to special-case SUSE:
  - If vendor_base is "suse" or vendor name starts with "opensuse", it returns name-version-revision.{rpm_abi}.rpm (omitting the distro tag).
  - Otherwise, it keeps the original behavior and includes both distro tag and ABI.
- They added a test to verify the SUSE filename omission in tests/platforms/linux/system/test_package.py.

Problems encountered during the fix and how they were resolved
- After introducing the SUSE special case, the agent initially accessed app.target_vendor_base directly. In some test contexts (e.g., create_command tests), first_app_config didn’t have target_vendor_base set, yielding an AttributeError.
- The agent fixed this by using getattr(app, "target_vendor_base", None) and also checking the vendor name prefix ("opensuse"), making the logic robust even when target_vendor_base isn’t set.

Gaps and risks in the implementation
- The change only adjusts distribution_filename. It relies on rpmbuild producing files in rpmbuild/RPMS/{abi}/ with the expected filename format. For SUSE, that is consistent, but if another RPM-based distro also omits the distro tag, this logic won’t catch it unless vendor_base is properly set or the vendor name follows a recognized pattern.
- rpm_tag() still returns el{codename} for non-fedora vendors. This is correct for RHEL family but irrelevant on SUSE because the new SUSE code path avoids using rpm_tag entirely. However, it’s good practice to avoid relying on vendor name ad hoc string checks where possible. A more robust approach would be detecting whether %{?dist} expands to empty in the build environment, but that would require invoking rpm which isn’t suitable for this path and test setup.
